# 疲劳系统需求与实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 `executing-plans` 逐任务实现此计划。步骤使用复选框（`- [ ]`）跟踪进度，并在每个审查点复核工作区与验证证据。

**目标：** 在普通副本有效切换房间时，为每名参与者扣除并立即持久化 1 点剩余疲劳，同时向 A21 客户端推送最新 UI；塔类、练习模式和 PVF 免疲劳副本不扣除，并支持普通角色 156、黑钻 188 与北京时间每日 06:00 回满。

**架构：** `DungeonFatigueService` 是疲劳业务与 SQLite 写入的唯一 owner。数据库保存“剩余疲劳”，协议投影时转换为客户端使用的“已消耗疲劳”；所有读取、入场校验和扣除都在事务内先执行日界校准，`ClockService` 只负责 06:00 在线通知，不作为持久化真源。

**技术栈：** C#、.NET 8、Microsoft.Data.Sqlite、现有 `ClockService`、`DailyResetService`、`PremiumService`、PVF `DungeonFile` 与项目 SelfTest。

---

## 1. 已确认需求

- `characters.fatigue` 保存剩余疲劳，而不是已消耗疲劳。
- 普通账号上限为 156；有效黑钻账号上限为 188。
- 普通副本每次有效 `MOVE_MAP` 扣 1 点；进入首房不扣。
- 组队切房时，每名实际随队切房的参与者各扣 1 点，并在一个数据库事务内提交，避免部分成员成功、部分成员失败。
- 扣除事务提交后立即发送 `ENUM_NOTIPACKET_FATIGUE`。
- 当前副本内疲劳降为 0 后允许完成本次副本；下次进入需要疲劳的副本时，服务端使用既有 `InsufficientFatigue` 拒绝原因拒绝。
- 死亡之塔、绝望之塔、普通副本练习模式、交互式练习场，以及 PVF 标记 `[no fatigue]`、`[enter without fatigue]` 的副本不扣疲劳，也不因疲劳为 0 拒绝入场。普通副本练习模式按当前 A21 `SELECT_DUNGEON` 的 `Flag1 == 0 && Flag2 != 0` 识别；`Flag1 != 0` 时 `Flag2` 仍属于深渊请求，不得误判为练习模式。
- PVF 标记 `[use fatigue only start dungeon]` 时不在后续切房扣除；本批次仍校验入场余额，不在缺少当前 A21 数值语义证据时新增入场扣值。
- 北京时间每日 06:00 回满。服务停机或角色离线跨过日界时，由下一次读取、登录、入场或扣除事务补做回满；在线角色由 `ClockService` 在 06:00 触发校准并推送 UI。
- 黑钻判断复用当前项目已验证的 `account_premiums.premium_type IN (1, 17)`，不新增第二套黑钻常量表。
- 疲劳药按当前 PVF `[add fatigue]` 的参数恢复剩余疲劳，恢复值不超过角色当前上限；物品扣除、每日可用次数和疲劳写入必须在 owned `InventoryLease` 的同一 SQLite 事务中提交，成功后立即发送 `NotiPacketTypeA21.FATIGUE`。

## 2. 当前问题与证据

- 当前 schema 版本为 v26，但基线 `item_schema.sql` 的 `characters` 表缺少疲劳列；新库会直接标记为当前版本，因此不会补跑历史 v20/v21 迁移。
- 历史 v20/v21 把 `fatigue` 默认成 0，并把 `maxFatigue` 默认成 188，与本次确认的“剩余疲劳、普通 156”合同不一致。
- `CharacterRecord` 与 `SqliteCharacterRepository` 没有加载疲劳数据。
- `SelectCharacterAckBodyBuilder` 固定发送 `0 / 188 / 0`，重登不会投影数据库状态。
- `DungeonMapHandler.HandleMoveMap` 当前只处理拓扑、机制和 `START_MAP`，没有疲劳事务或 UI 通知。
- A21 客户端当前二进制的 `ENUM_NOTIPACKET_FATIGUE (0x0024)` handler 连续读取 5 个小端 `UInt16`。与 `SELECT_CHARACTER` ACK 的同一组 setter 对照后，字段顺序为：已消耗、上限、额外已消耗、疲劳电池、成长 Buff。
- 当前 A21 实机普通进入副本 156 的 `SELECT_DUNGEON` body 为 `9C-00-00-00-00-00-00-FF-FF-00-00-00-00-00-00`；同副本练习模式为 `9C-00-00-00-01-00-01-FF-FF-00-00-00-00-00-00`。难度字节独立变化，练习信号是非深渊请求下的 `Flag2=1`。
- PVF 模型已经解析 `NoFatigue`、`EnterWithoutFatigue`、`UseFatigueOnlyStartDungeon`、`Fatigue` 和 `FatigueResult`，无需硬编码副本 ID。
- 当前 A21 疲劳药右键发送 `CmdPacketTypeA21.USE_STACKABLE_ACTION (0x0204)`；其包体偏移 7 是动作参数而非 itemId，物品身份必须由服务端 owned 背包槽位解析。实测物品 `0x0029F58A` 的 PVF 为 `[add fatigue] 1`、`[total usable count] 3`；未实现的动作包必须拒绝，不能无效果地扣除物品。

## 3. 数据合同

### 3.1 `characters` 字段

```sql
fatigue          INTEGER NOT NULL DEFAULT 156,
usedFatigue      INTEGER NOT NULL DEFAULT 0,
maxFatigue       INTEGER NOT NULL DEFAULT 156,
fatigue_reset_day INTEGER NOT NULL DEFAULT 0
```

- `fatigue`：当前剩余基础疲劳，范围为 `0..maxFatigue`。
- `usedFatigue`：A21 协议中的额外疲劳已消耗值；本批次不实现额外疲劳来源，保持 0。
- `maxFatigue`：最近一次校准出的上限，普通 156、黑钻 188。
- `fatigue_reset_day`：使用 `DailyResetService.TodayId(utcNow)` 计算的游戏日 ID。

### 3.2 schema v27

对 v26 存量数据库执行连续迁移：

```sql
ALTER TABLE characters ADD COLUMN fatigue INTEGER NOT NULL DEFAULT 156;
ALTER TABLE characters ADD COLUMN usedFatigue INTEGER NOT NULL DEFAULT 0;
ALTER TABLE characters ADD COLUMN maxFatigue INTEGER NOT NULL DEFAULT 156;
ALTER TABLE characters ADD COLUMN fatigue_reset_day INTEGER NOT NULL DEFAULT 0;
```

迁移先记录 v27 执行前是否已经存在 `fatigue`。若不存在，则按新合同新增；若存在，则把历史“已消耗值”一次性换算为剩余值。两种情况都先按有效黑钻 premium type `1/17` 算出 188 或 156 的当前上限：新列取 `fatigue=maxFatigue`，历史列取 `fatigue=maxFatigue-clamp(旧 fatigue, 0, maxFatigue)`。迁移同时写入执行时对应的游戏日 ID，避免服务部署后首次登录错误回满并丢失当天已消耗值。不得改写已发布的 v20-v22。

### 3.3 A21 协议投影

```text
UInt16 totalFatigue        = maxFatigue - fatigue
UInt16 maxFatigue          = maxFatigue
UInt16 usedFatigue         = usedFatigue
UInt16 fatigueBattery      = initializationSnapshot.AckFatigueBattery 或 0
UInt16 fatigueGrownUpBuff  = initializationSnapshot.AckFatigueGrownUpBuff 或 0
```

所有值先夹紧到 `UInt16` 范围。包名只引用 `NotiPacketTypeA21.FATIGUE`，不在业务代码重复维护 opcode。
